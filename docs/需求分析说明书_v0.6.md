## 1. 问题定义

### 1.1 目标用户的真实处境

一个玩整合包（Create + 农夫乐事 + 建筑类 mod）的生存玩家，在**中期之后**会遇到以下状态：

| 症状 | 具体表现 |
|---|---|
| 产能过剩 | 自动化农场一小时产出数百食物，玩家吃不完 |
| 消耗无意义 | 多出来的食物只能丢岩浆、塞箱子烂掉 |
| 建造失焦 | 想盖好看的建筑，但"盖了也没人看、没用" |
| 内容闲置 | 原版几十种动植物只有观赏价值，看一眼就忘 |
| 动力衰减 | 装备齐了、机器全了，不知道该干什么 |

### 1.2 根因

> **玩家的产出没有"去处"，玩家的建设没有"对象"。**

原版 Minecraft 的所有系统都指向"玩家自己"——你种田是为了自己吃，你盖房是为了自己住。当"自己"的需求被满足后，整个循环就停转了。

### 1.3 现有方案的不足

| 现有做法 | 为什么不够 |
|---|---|
| 加更难的 Boss / 更强的装备 | 延长了流程，没有解决循环问题 |
| 加新的自动化机器 | 进一步加剧产能过剩 |
| 原版村民交易 | 交易是"资源换资源"，没有情感连接，且需求固定 |
| 殖民地类 mod（MineColonies 等） | 偏"管理模拟"，UI 重、学习成本高，且 NPC 是"人力资源"不是"人" |

### 1.4 本项目的解法

> **引入"有需求的居民"作为新的消耗端与建设对象。**
>
> 玩家用过剩的资源供养居民 → 居民回馈"替玩家做他懒得做的事" → 玩家的基地因此从"工厂"变成"镇子"。

## 2. 设计目标与非目标

### 2.1 设计目标（按优先级）

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | **给过剩产能一个去处** | 中后期玩家的食物有稳定消耗渠道，且消耗量级与自动化产能匹配 |
| G2 | **给玩家的付出一个回报** | 居民会替玩家承担"重复、机械、机器做起来很丑"的工作 |
| G3 | **给建造一个对象** | 玩家会因为"某个人"而主动改造建筑、开辟产线、寻找动植物 |
| G4 | **给原版闲置内容赋予意义** | 特定动植物/食物/装饰因为"有人需要"而重新产生价值 |
| G5 | **产生情感连接** | 玩家能记住每个居民的名字与偏好，并愿意为其付出 |
| **G6** | **成为平台而非内容包** | 第三方可新增专长、行为、食物分类，无需改动本 mod 代码 |

### 2.2 非目标（明确不做）

| 编号 | 不做 | 理由 |
|---|---|---|
| N1 | 完整的殖民地经营模拟 | 工作量为数月级，且与 MC 的交互习惯冲突 |
| N2 | NPC 真实寻路去远处挖矿/砍树 | 寻路难、区块加载难、易出 bug（会掉岩浆） |
| N3 | 需求管理面板 / 满意度数值面板 | 会把"养成"退化为"填表"，破坏沉浸感 |
| N4 | 建筑评分 / 检测系统 | 会变成"照图纸摆方块"的枯燥劳动 |
| N5 | NPC 死亡惩罚（饿死 / 病死） | 玩家离线几天回来发现全村死光，会产生强烈负面情绪 |
| N6 | 与 Create 争夺"自动化"领地 | Create 做机器更高效也更"好玩"，抢不过也不必抢 |
| N7 | 首发即支持多套人物模型 | 美术成本高，先用原版模型，留扩展接口 |
| **N8** | **写死对任何具体 mod 的支持** | 一律走标签 / 组件 / 默认推断，见 §4.2 |
| **N9** | **为劳动写死具体专长逻辑** | 一律走行为原语 + 数据配置，见 §4.4 |

### 2.3 平台化定位（新增）

> **本 mod 不追求"支持 N 个 mod"，而追求"任何符合约定的 mod 都能被支持"。**

具体体现：

| 扩展点 | 谁可以扩展 | 扩展方式 |
|---|---|---|
| 食物分类 | 整合包作者 / 任意 mod | 数据包标签（`data/*/tags/item/...`） |
| 专长定义 | 整合包作者 / 任意 mod | json 数据驱动 |
| 行为原语的目标匹配 | 任意 mod | 给方块/物品打标签 |
| 对话文本 | 整合包作者 | 语言文件 + 数据包 |

**代价**：初期需要多做一些"约定"和"默认推断规则"。
**收益**：mod 活得久、整合包作者愿意用、生态能长出来。

## 3. 核心循环

### 3.1 主循环

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│   玩家产能过剩                                                │
│        │                                                     │
│        ▼                                                     │
│   居民消耗食物（品质越高，能养的人越多）                        │
│        │                                                     │
│        ▼                                                     │
│   居民满意度上升 → 愿意工作                                    │
│        │                                                     │
│        ▼                                                     │
│   居民替玩家做"机器做不了/做起来丑"的事                         │
│        │                                                     │
│        ▼                                                     │
│   玩家省下无聊劳动 → 基地更像"镇子"                            │
│        │                                                     │
│        ▼                                                     │
│   玩家有更多时间与动力扩张 → 产能进一步过剩                     │
│        │                                                     │
│        └──────────────────────────────────────────────────────┘
```

### 3.2 三条副线（加速器）

| 副线 | 玩家行为 | 回流效果 |
|---|---|---|
| **建筑线** | 按居民偏好改造住宅 | 满意度提升 → 工作效率提升 |
| **食物线** | 为居民开特定作物/料理产线 | 满意度提升 → 解锁特殊对话/能力 |
| **动植物线** | 寻找特定动植物送给居民 | 触发特殊事件 → 玩家获得"成就感"与小回馈 |

### 3.3 三条附加成长轴（v0.2 新增）

主循环之外，玩家还有三条**长期**目标，避免"循环跑通后就没事干"：

| 轴 | 内容 | 驱动力 |
|---|---|---|
| **收集轴** | 刷到稀有组合（如"挖矿 IV + 爱甜食 + 怕水"） | 随机性 |
| **养成轴** | 把某个居民养成"大师"（§4.5） | 熟练度 |
| **建设轴** | 为居民改造建筑、开辟产线、寻找动植物 | 偏好满足 |

### 3.4 循环的健康性判据

设计评审时用这三条检验每个功能：

1. **倒岩浆测试**：如果这个功能只是"消耗资源"，那它和倒岩浆有区别吗？
2. **Create 测试**：这件事如果让 Create 做，会不会显得很蠢？如果不会，别做。
3. **记名测试**：玩家能说出"我为他做这件事"的那个"他"是谁吗？说不出，就是无效设计。

## 4. 系统设计

### 4.0 镇民机制骨架（v0.3 新增，顶层结构）

> **本章先确立"镇民是什么"，再分述各子系统。** 后续所有功能新增，都要先回答"它属于哪一层"。

#### 4.0.0 一句话定义

> **镇民是一个会饿、会挑、会记、会累的人形居民；你养他，他替你干一件事。**

**这句话是所有机制的校验标准。** 任何新特性加入前，先问它服务"会饿 / 会挑 / 会记 / 会累"中的哪一个；一个都不服务，就不该加。

#### 4.0.1 七层结构

| 层 | 名称 | 回答的问题 | 核心内容 | v0 |
|---|---|---|---|---|
| **L1** | 生理层 | 他会饿吗？ | 饥饿值、进食、食物价值、饿的后果 | ✅ |
| **L2** | 劳动层 | 他会做什么？ | 动作原语 + 专长、工位、干活循环 | ✅ |
| **L3** | 人格层 | 他会挑吗？ | 饮食偏好、环境偏好、怪癖 | ✅ |
| **L4** | 状态层 | 他会累、会烦吗？ | 满足度、熟练度 | ✅ |
| **L5** | 记忆层 | 他记得你吗？ | 事件记忆、台词引用 | ⏳ |
| **L6** | 表达层 | 他怎么告诉你？ | 气泡 + 右键 UI + 自言自语 + 行为暗示 | ✅ |
| **L7** | 归属层 | 他属于哪里？ | 聚落核心、家（床）、工位、食物区 | ✅ |

#### 4.0.2 层间依赖（决定实现顺序）

```
L1 生理（饿）
   └─ 饿了要打断 → L2 劳动
L2 劳动（动作原语 + 专长）
   └─ 干活产生经验 → L4 状态
L3 人格（偏好 / 怪癖）
   └─ 调制 L1 的食物价值 与 L4 的满足度
L4 状态（满足度 / 熟练度）
   └─ 状态变化需要输出 → L6 表达
L6 表达（气泡 / UI / 自语）
   └─ 引用历史 → L5 记忆
L7 归属
   └─ 为 L1/L2 提供"去哪"的坐标
```

> **关键结论：L2（劳动）必须早于 L1（饥饿）。**
> 没有劳动，就没有"吃饱了去干活"的因果链，饥饿只是一个孤立的倒计时。
> 因此实现顺序为 **L2 → L1 → L4 → L3 → L7 → L6 完善 → L5**。

#### 4.0.3 共同特性（所有镇民必须有的，与职业无关）

| 特性 | 定义 | 玩家能感知到什么 |
|---|---|---|
| **有名字** | 随机中文小名，永远显示在头顶 | "那个叫阿杏的" |
| **有身体** | 会走、会看你、会浮水、不会刷没 | 它是活的，不是贴图 |
| **有饥饿** | 饥饿值下降，需要进食 | 它会走开去吃饭 |
| **有偏好** | 爱吃什么、喜欢什么环境 | 喂对东西它更开心 |
| **有怪癖** | 一定有"不想干的事" | 它不是完美工人 |
| **有记忆点** | 一句话能被描述出来 | "怕光、爱吃甜的园丁" |
| **有归属** | 属于某个聚落、某张床 | 它晚上会回去 |
| **不用数字说话** | 状态用气泡/台词/行为表达 | 不需要算最优解 |

**三条硬约束**（v0.2 已有，v0.3 强化）：

1. **必须能被一句话描述** —— 写不出来，这个组合不该出现在生成池。
2. **必须有"不想干的事"** —— 完美工人会被当机器用。
3. **必须记得玩家做过什么** —— 一句"你上次给的蛋糕还有吗"比十个数值有效。

#### 4.0.4 明确排除在骨架之外

| 排除项 | 理由 |
|---|---|
| ❌ 居民结婚 / 生育 | 成本极高，且会让玩家把镇子当育婴室 |
| ❌ 居民之间的社交 | 看起来美好，实际是 NPC 对着空气演，玩家看不到价值 |
| ❌ 居民偷窃 / 闹事 | 负反馈机制，会让玩家把镇民当敌人 |
| ❌ 饿死 | 玩家出门三天回来全死光，是最容易劝退的设计（见 D13） |

#### 4.0.5 与旧章节的对应关系

| 骨架层 | 对应旧章节 |
|---|---|
| L1 生理 | §4.3 食物与消耗系统 |
| L2 劳动 | §4.4 劳动行为系统 |
| L3 人格 | §4.1.2 属性构成、§4.8 动植物系统 |
| L4 状态 | §4.5 熟练度系统、§4.7.2 满意度光谱 |
| L5 记忆 | §4.1.2 `memory` 字段、Q16 |
| L6 表达 | §4.6 需求表达系统（v0.3 已改写） |
| L7 归属 | §4.7 建筑与空间语义 |

### 4.1 居民（NPC）

#### 4.1.1 生成方式

**组合随机，枚举固定；外形先统一，预留多样化扩展。**

```
居民 = 外形 + 专长 + 偏好 + 怪癖 + 名字 + 熟练度
         │      │        │       │       │        │
      固定池   枚举     枚举    枚举   随机生成   初始为 1
      (v0:    (数据     (数据   (数据            (可迁移/可成长)
      原版村民)  驱动)    驱动)   驱动)
```

**生成源** `【待定 D1】`：

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| S1 流浪商人式 | 定期在玩家附近刷新，可招募 | 无需世界生成；有"来客"仪式感 | 刷新位置与频率需调 |
| S2 特殊结构 | 玩家放置某种结构方块后生成 | 玩家可控，节奏自定 | 需新增方块与交互设计 |

> **倾向**：v0 采用 S1，S2 作为后续扩展。

#### 4.1.2 属性构成（v0.3 重构为五组）

> **v0.3 修订**：原表把 12 项属性平铺成一张表，无法区分"数值 / 枚举 / 容器 / 引用"。
> 现按**数据性质**重分为五组，并逐项标注实现阶段。

##### A 组 · 状态（会随时间改变）

| 属性 | 类型 | 范围 | 变化 | 阶段 |
|---|---|---|---|---|
| `health`（血量） | `float` | 0~20 | 受伤/回血，走原版 `Attributes` | ✅ S1 |
| `hunger`（饥饿） | `int` | 0~100 | **随时间下降**，进食回升 | S3 |
| `mood`（心情） | `int` | 0~100，有初值 | **每日结算 + 事件驱动**，见 §4.10 | S4 |

##### B 组 · 身份（生成时确定，基本不变）

| 属性 | 类型 | 说明 | 阶段 |
|---|---|---|---|
| `name` | 字符串 | 随机中文小名，20 个池 | ✅ S1 |
| `appearance` | 固定 | v0 统一复用原版村民模型 | ✅ S1 |
| `profession`（特长 / 职业） | 复合对象 | **含：职业类型 + 该项的熟练度**，见 §4.4.3 | S2 |
| `hobbies`（爱好） | 复合对象 | **多组**：饮食 / 家中物品 / 生物 / 人，见 §4.1.2.1 | S5 |
| `dislikes`（厌恶） | 复合对象 | 与 `hobbies` **结构对称**，见 §4.1.2.1 | S5 |
| `personality`（性格） | 枚举 | 与怪癖合并，见 §4.1.2.2 | S5 |

##### C 组 · 归属（指向其他对象）

| 属性 | 类型 | 说明 | 阶段 |
|---|---|---|---|
| `town`（所属城镇） | 引用 `TownData` | 镇民维护在城镇成员列表中；也可为空（流浪中） | S6 |
| `residence`（住所） | 引用方块坐标 | **每人单独分配**（D24） | S6 |
| `currentJob`（当前工作） | 复合对象 | 干什么 + 在哪干 + 是否暂停 | S2 |
| `foodAreas`（食堂） | 引用列表 | **由城镇自动绑定，全城共用**（D24） | S6 |

##### D 组 · 容器

| 属性 | 类型 | 容量 | 说明 | 阶段 |
|---|---|---|---|---|
| `inventory`（物品栏） | 物品列表 | 建议 9~27 格 | 他自己的背包：种子、工具、收成 | S2 |

##### E 组 · 关系

| 属性 | 类型 | 说明 | 阶段 |
|---|---|---|---|
| `affection`（好感度） | `int` 0~100 | **对玩家**的长期态度，缓慢累积，与 `mood` **不同**（D21） | S4 |
| `relations`（喜欢的人） | `Map<UUID, int>` | 对其他 NPC 的好感，N² 复杂度，见 Q32 | ⏳ |
| `memory`（记忆） | 列表 | 记住玩家做过的事 | ⏳ S8 |
| `dialogue_lines` | 数据表 | 按状态/事件触发的台词 | S7 |

##### 4.1.2.1 爱好与厌恶的结构（v0.3 新增）

> **用户定义**："爱好应该有多个"，且**有喜欢的就一定要有讨厌的**。
> 因此 `hobbies` 与 `dislikes` **共用同一套维度定义**，只是正负相反。

| 维度 | 判定对象 | 判定方式 | 作用范围 | 阶段 |
|---|---|---|---|---|
| **饮食** | `ItemStack` | `c:foods/*` 标签（见 §4.2.3） | 喂食时 | S5 |
| **家中物品** | 方块 / 物品 / **材质** | 方块标签 + 材质 tag（`minecraft:planks` 等） | 住所半径内空间查询 | S5 |
| **生物** | 实体类型 | 实体标签 | 住所半径内实体扫描 | ⏳ |
| **人** | 其他镇民 UUID | 直接引用 | 行为倾向（靠近/回避） | ⏳ |

**数据结构（示意）**：

```java
record Hobby(HobbyKind kind, ResourceLocation target, int weight) {}
// kind: DIET / HOME_OBJECT / CREATURE / PERSON
// target: 标签 id 或实体 id 或 UUID
// weight: 权重 1~3（"特别喜欢"给 3）
```

**关键约束**：`hobbies` 至少 1 项、`dislikes` 至少 1 项。
→ 这是 §4.1.3 第 2 条"必须有不想干的事"的**数据化落地**。

##### 4.1.2.2 性格与怪癖的合并（v0.3 修订）

原文档把 `quirk`（怪癖）单列。v0.3 把它并入 `personality`：

| 子项 | 数量 | 例子 |
|---|---|---|
| **性格倾向** | 1 个 | 开朗 / 沉默 / 急躁 / 温和 / 懒散 |
| **怪癖** | 0~2 个 | 避光、怕水、爱动物、社恐、夜行 |

**为什么合并**：性格决定"说话风格"，怪癖决定"行为限制"，二者共同构成"这个人是什么样的"，拆开会导致生成时难以保证组合合理性。

#### 4.1.3 居民"人格化"的三条硬约束

1. **必须能被一句话描述**
   例："爱吃甜食的僵尸，怕光，养了只黑猫。"
   描述不出来 → 该组合不该出现在生成池里。

2. **必须有"不想干的事"**
   完美工人会被当机器用。居民需要休息、闲逛、拒绝过度劳动。
   → v0.3 落地为：`dislikes` **不能为空**。

3. **必须记得玩家做过什么**
   "你上次给我的那种卷饼，还有吗？"——这一句比十个数值更能产生连接。

### 4.2 内容识别层（v0.2 新增，核心技术决策）

#### 4.2.1 需求

> 居民要知道"什么算食物""什么算甜食""什么算花"，但**绝不能写死具体物品列表**。

#### 4.2.2 三级识别策略

```
判断"这个东西是 X 类"

① 标签优先：item.is(TagKey)                        ← 最准，权威来源
② 组件次之：DataComponents.FOOD 存在？
              读 nutrition / saturation 做推断       ← 覆盖所有原版+mod 食物
③ 字符串兜底：注册 id / 显示名做启发式匹配           ← 保底，永不为空
```

#### 4.2.3 第一层：物品标签（Item Tags）

- **命名空间约定**：优先使用 `c:`（Common Tags，Fabric/NeoForge 共用标准）
- **自定义语义标签**：本 mod 定义一套，允许被整合包覆盖

##### 4.2.3.1 v0.3 实测结论：原版已提供大部分食物分类

> **v0.3 关键发现**：`c:foods` 系列标签在 1.21 已经**内置 14 个子分类**，且原版食物已填好。
> 因此「荤 / 素 / 生 / 熟 / 鱼 / 汤 / 面包 / 派 / 水果 / 浆果」**全部不需要我们手写**。

| 标签 | 原版已填内容 | 我们是否需要补 |
|---|---|---|
| `c:foods` | 全部可食用物品 | ❌ 不用 |
| `c:foods/fruit` | apple, golden_apple, enchanted_golden_apple, melon_slice, chorus_fruit | ❌ |
| `c:foods/vegetable` | beetroot, carrot, golden_carrot, potato | ❌ |
| `c:foods/berry` | sweet_berries, glow_berries | ❌ |
| `c:foods/raw_meat` | beef, chicken, mutton, porkchop, rabbit | ❌ |
| `c:foods/cooked_meat` | cooked_beef, cooked_chicken, cooked_mutton, cooked_porkchop, cooked_rabbit | ❌ |
| `c:foods/raw_fish` | cod, salmon, pufferfish, tropical_fish | ❌ |
| `c:foods/cooked_fish` | cooked_cod, cooked_salmon | ❌ |
| `c:foods/soup` | beetroot_soup, mushroom_stew, rabbit_stew, suspicious_stew | ❌ |
| `c:foods/bread` | bread | ❌ |
| `c:foods/cookie` | cookie | ❌ |
| `c:foods/pie` | pumpkin_pie | ❌ |
| `c:foods/golden` | golden_apple, enchanted_golden_apple, golden_carrot | ❌ |
| `c:foods/food_poisoning` | chicken, rotten_flesh, spider_eye, pufferfish, poisonous_potato | ❌ |
| `c:foods/candy` | **空标签**（留给 mod 填） | ✅ **需补**（见 4.2.3.2） |

**推论**：需求文档原先设计的"自定义食物分类体系"大幅缩水。
真正需要本 mod 亲手定义的，**只有「甜」这一个维度**。

##### 4.2.3.2 「甜食」标签：v0 唯一需要手写的分类 `【已定 D19】`

`c:foods/candy` 在原版是空标签，仅 `cookie` / `pie` / `cake` 有各自独立标签。
为了让"爱吃甜食的镇民"在纯原版下也有食可吃，本 mod 补一份甜食清单：

```json
// src/main/resources/data/c/tags/item/foods/candy.json
{
  "replace": false,
  "values": [
    "minecraft:cookie",
    "minecraft:cake",
    "minecraft:pumpkin_pie",
    "minecraft:honey_bottle",
    "minecraft:sweet_berries",
    "minecraft:glow_berries",
    "minecraft:melon_slice",
    "minecraft:golden_apple",
    "minecraft:enchanted_golden_apple",
    "minecraft:cocoa_beans"
  ]
}
```

**设计要点**：

| 要点 | 说明 |
|---|---|
| 直接写进 `c:` 命名空间 | 不是 `bmfstown:`。这样**其他 mod 也会认这份定义**，未来联动农夫乐事时双方自动互通 |
| `"replace": false` | 不覆盖他人内容，只做**追加**。任何 mod 往 `c:foods/candy` 里加东西都不会冲突 |
| 只收"加工甜食 + 天然甜果" | 不把 `sugar` / `cake`（方块形态）之类的原料算进去 |
| 排除咸、辣、冷、热 | 原版无此概念，强行造会别扭。见 D20 |

##### 4.2.3.3 扩展位：农夫乐事（Farmer's Delight）联动

> **用户明确要求**："后续我想要让农夫乐事也联动起来"。

v0 不装硬依赖，但**在标签层面预留好接口**，联动时只加 json、不改代码：

```json
// 农夫乐事的食物大多已自行填入 c:foods/* 系列
// 我们只需在甜食标签里追加它们的条目
{
  "replace": false,
  "values": [
    {"id": "farmersdelight:sweet_roll",        "required": false},
    {"id": "farmersdelight:apple_pie",         "required": false},
    {"id": "farmersdelight:sweet_berry_cookie","required": false},
    {"id": "farmersdelight:honey_cookie",      "required": false},
    {"id": "farmersdelight:melon_popsicle",    "required": false},
    {"id": "farmersdelight:glow_berry_custard","required": false}
  ]
}
```

- `required: false` 是**关键**：没装农夫乐事时这些条目被静默忽略，不会崩
- 装了之后自动生效，**不需要玩家做任何配置**
- 同理适用于任何食物 mod（`required: false` 的通用模式）

##### 4.2.3.4 口味维度的最终取舍

| 维度 | 数据来源 | v0 |
|---|---|---|
| 荤 / 素 / 鱼 / 水果 / 蔬菜 / 浆果 | `c:foods/*`（原版已填） | ✅ 直接用 |
| 生 / 熟 | `c:foods/raw_*` ↔ `c:foods/cooked_*` | ✅ 直接用 |
| 汤 / 面包 / 派 / 曲奇 | `c:foods/*` | ✅ 直接用 |
| **甜** | 本 mod 补 `c:foods/candy` | ✅ 见 4.2.3.2 |
| 咸 | 无标准，可定义为"非甜非素的剩余" | ⏳ 见 D20 |
| 辣 | 原版无，需跨 mod 猜测 | ❌ 不做 |
| 冷 / 热 | 原版无温度概念 | ❌ 不做 |
| 金制食物 | `c:foods/golden` | ✅ 可直接作为"稀罕物"维度使用 |

`【存疑 Q28】` 见第 11 章：甜食标签的"咸甜互斥"判定是否会误伤。

##### 4.2.3.5 自定义标签的写法规范

- **命名空间约定**：优先使用 `c:`（Common Tags，Fabric/NeoForge 共用标准）
- **本 mod 专属语义标签**才用 `bmfstown:`，例如 `bmfstown:food/sweet`（若将来需要更细粒度）
- `required: false` 是跨 mod 兼容的**唯一正确写法**：没装该 mod 也不崩，装了自动生效
- **同时提供默认推断规则**：标签未覆盖时，走 ② 和 ③

#### 4.2.4 第二层：数据组件（`DataComponents`）

1.20.5+ 起，食物属性已迁移为数据组件，这是**跨 mod 的天然通用载体**：

```java
FoodProperties food = stack.get(DataComponents.FOOD);
if (food != null) {
    int nutrition    = food.nutrition();     // 营养值
    float saturation = food.saturation();    // 饱和度
    boolean always   = food.canAlwaysEat();
}
```

**意义**：任何 mod 做的食物，只要是"能吃的"，必然带这个组件。**不需要知道它叫什么，就能拿到它的数值属性。**

#### 4.2.5 第三层：字符串兜底

```java
ResourceLocation id = BuiltInRegistries.ITEM.getKey(stack.getItem());
String name = stack.getHoverName().getString();
// 用 id / name 做关键词匹配（如含 sweet / cake / pie → 甜食）
```

#### 4.2.6 为什么不用反射

| 方式 | 评价 |
|---|---|
| 反射读取他 mod 的类 | ❌ 慢、脆弱（混淆名一变就崩）、无法处理未加载的类、难调试 |
| **标签 + 组件** | ✅ 快、稳定、官方支持、跨 mod 通用 |

> **反射的正当用途**是"跨 mod 可选集成"（`Class.forName` 探测某 mod 是否存在），**不用于内容识别**。

`【存疑 Q1】` 见第 11 章：三级策略的优先级冲突 / 性能开销。

### 4.3 食物与消耗系统

#### 4.3.1 需求描述

- 玩家**划定一个食物区**
- 居民会自行前往食物区进食
- 食物消耗应当与自动化产能**同量级**

#### 4.3.2 消耗计算方式 `【待定 D2】`

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| F1 按个数 | 每个居民每天吃 N 个食物 | 简单直观 | 廉价食物可轻易满足，规模化农业仍过剩 |
| F2 按品质 | 每种食物有"饱食分"，每天需 S 分 | 让精致料理有价值；农夫乐事内容被激活 | 需要一张食物分值表（可由组件推断，不必手写） |
| F3 混合 | 个数决定"吃饱"，品质决定"满足" | 兼顾两者 | 实现略复杂 |

> **倾向 F3**：基础消耗用个数（保证量级匹配），额外满意度用品质（保证精致料理有意义）。
> **补充**：F2 的"分值表"现在**不必手写**——可直接由 `DataComponents.FOOD` 的 nutrition/saturation 计算，见 §4.2.4。

#### 4.3.3 "食物区"的实现形态 `【待定 D3】`

| 方案 | 描述 |
|---|---|
| Z1 专用方块 | 放置"餐桌/食槽"方块，居民到附近进食，方块绑定一个容器 |
| Z2 容器标记 | 玩家用工具右键某个容器，标记为"食物来源" |
| Z3 范围判定 | 以聚落核心为圆心，半径内所有容器算作食物来源 |

> **倾向 Z1**：有实体感（玩家能看到"饭桌"），实现简单，天然形成"食堂"这种聚落空间。

#### 4.3.4 离线问题 `【待定 D6】`

> **倾向：不消耗。** 玩家离线时世界不 tick，回来时粮仓还在。这是 N5 的延伸——不能让玩家因为"出差三天"而受罚。

#### 4.3.5 饥饿的后果 `【待定 D13】`

| 方案 | 描述 | 后果 |
|---|---|---|
| H1 会饿死 | 饥饿归零后掉血，最终死亡 | 玩家出门三天回来全死光，**最劝退** |
| H2 不干活 | 饥饿归零 → 罢工 + 抱怨，但不会死 | 惩罚是"效率损失"，不是"资产损失" |
| H3 只抱怨 | 饥饿归零 → 只冒气泡，照常干活 | 饥饿形同虚设 |

> **强烈倾向 H2。** 理由：
> - 饥饿的意义是**制造"照顾他"的压力**，不是制造"破产风险"
> - 死亡不可逆（除非做复活机制），而"不干活"可逆，玩家随时能补救
> - 与 N5（不惩罚离线）一致

**注**：若玩家坚持要"会饿死"，应配套**可复活机制**（如床/城镇核心处重生），否则不推荐。

### 4.4 劳动行为系统（v0.2 新增，核心架构决策）

#### 4.4.1 设计原则

> **不写死"园丁会种花""厨师会做饭"，而是抽象出"人能做的动作"。**
> **专长 = 行为原语 + 目标过滤器，用数据配置，不用代码硬编码。**

#### 4.4.2 八个行为原语

| 原语 | 语义 | 参数 |
|---|---|---|
| `WANDER` | 在区域内游荡 | 区域、时长 |
| `INTERACT` | 对某方块使用（右键语义） | 目标方块/标签、手持物过滤器 |
| `MINE` | 挖掘某方块 | 目标方块/标签 |
| `PLACE` | 放置某方块 | 方块/标签、位置规则 |
| `ATTACK` | 攻击某实体 | 目标类型/标签 |
| `DELIVER` | 把物品从 A 送到 B | 起点、终点、物品过滤器 |
| `CONSUME` | 消耗某物品 | 物品过滤器 |
| `SIT` | 坐下/待着 | 位置、时长 |

**共同特征**：每个原语都是"玩家本来就能做的一个动作"，区别只在于"谁做、在哪做、对什么做"。

#### 4.4.3 专长 = 数据配置

```json
{
  "specialty": "gardener",
  "behaviors": [
    {"type": "wander",   "area": "work_zone", "duration": 600},
    {"type": "interact", "target_tag": "mymod:plants", "item_filter": "mymod:watering_can"},
    {"type": "place",    "block_tag": "mymod:flowers",  "position": "work_zone"},
    {"type": "mine",     "target_tag": "mymod:weeds"}
  ]
}
```

换成"厨师"，**只换数据，不改代码**：

```json
{
  "specialty": "cook",
  "behaviors": [
    {"type": "interact", "target_block": "minecraft:campfire", "item_filter": "c:foods"},
    {"type": "deliver",  "from": "food_area", "to": "kitchen"}
  ]
}
```

#### 4.4.4 收益

| 维度 | 改前 | 改后 |
|---|---|---|
| 加一个专长 | 改代码 | **加一份 json** |
| 与其他 mod 方块交互 | 单独适配 | **标签自动匹配** |
| 玩家/整合包自定义 | 做不到 | **可以做** |
| 代码量 | N 专长 × M 行为 | **N 原语 + 一份数据表** |

#### 4.4.5 抽象层的边界

**只做 6–8 个原语，不做循环、条件、变量。**

组合性靠两件事实现：
- **序列**：做 A，然后做 B
- **过滤器**：对满足条件的 X 做 A

> 否则会滑向"自研脚本语言"，工作量与维护成本失控。`【存疑 Q3】`

#### 4.4.6 工位模型（与行为原语的关系）

**工坊内**：不真寻路，小范围位移或"瞬移式作业"
**工坊外**（游荡、巡逻）：真寻路，但范围有限（如 16 格内）、降频
**挖/放**：仅限**已加载区块**内、玩家附近（如 32 格内）

> **核心原则**：**NPC 只在"玩家能看到的地方"干活，看不见的地方不 tick。**
> 既省性能，也符合直觉（玩家不在，就没人干活）。

#### 4.4.7 工作类型的边界

**只做"机器做不了 / 机器做起来丑"的事。**

| ✅ 适合交给居民 | ❌ 不适合（交给 Create） |
|---|---|
| 装饰性建造（铺路、种花、挂灯笼） | 收菜、播种 |
| 巡逻、灭火、修补被破坏的墙 | 挖矿（大范围） |
| 做饭、招待来访者（社交性行为） | 熔炼、合成 |
| 照顾动物、打理花园 | 物流运输 |
| 夜间守卫 | 大规模批量加工 |

`【存疑 Q4】` 见第 11 章：行为原语的"机器人感"。

### 4.5 熟练度系统（v0.2 新增）

#### 4.5.1 设计意图

> **让"养"有长期回报。** 没有它，NPC 第一天和第一百天没有区别。

#### 4.5.2 三层作用

| 层次 | 效果 | 作用 |
|---|---|---|
| **速度** | 做得更快 | 最直观，但容易碰到天花板 |
| **质量** | 产出更好（如厨师做出更高品质的食物） | 让老 NPC 有独占价值 |
| **范围** | 能做更多种类的事 | 打开玩法深度 |

> **倾向**：三层都要有，但速度成长放缓，**质量与范围更明显**。否则玩家只会觉得"又是一个加速 buff"。

#### 4.5.3 成长规则

**核心问题：单调重复就能涨吗？** 如果挂机就涨，会变成刷级。

| 涨法 | 是否算数 |
|---|---|
| 重复做同一件事 | 涨，但**递减**（第 100 次挖同样方块几乎不涨） |
| 做**新种类**的事 | 涨得多（第一次种花、第一次种树都给大经验） |
| 做**符合偏好**的事 | 涨得更多（爱吃甜的厨师做甜点，涨得快） |
| 做**难度更高**的事 | 基础经验更高 |

> **设计效果**："练级"的前提是**不断拓展内容**，正好和"让玩家去开新产线"的目标咬合。

#### 4.5.4 上限与展示

- **上限**：软上限（如 Lv.10），后面增长极慢
- **展示**：**不显示数字**，用称号

| 等级 | 称号 |
|---|---|
| 1–2 | 新手 |
| 3–5 | 熟练 |
| 6–8 | 老手 |
| 9–10 | 大师 |

#### 4.5.5 与其他系统的关系

- 与**收集轴**互补：玩家会想"刷到一个园丁，把它养到大师，看看大师级能做什么"
- 与**满意度**正交：满意度决定"愿不愿意干"，熟练度决定"干得多好"

`【存疑 Q5】` 见第 11 章：熟练度的天花板与数值曲线。

> **v0.5 落地情况**：v1 已实现——10 段位累计经验阶梯（0/100/250/500/900/1500/2400/3600/5200/7500，生疏/入门/熟练/精通/老练/专家/大师/宗师/传奇/神话），三技能共用；perk 解锁点 3/6/9 已留数据位；经验入账入口 `addSkillXp`，当前唯一来源=战士击杀(+30，可配)。阈值定为存档语义，不配置化。
>
> **v0.6 落地情况**：v2——数值作用第一层（效率）接入战士：`0.6+0.1×(段位−1)`，经临时 AttributeModifier 乘进近战伤害（武器无关）；perk 天赋整链路实装（节点 3/6/9、六天赋、选档 UI、声光反馈），perk 全部数值进 `perk.*` 配置、描述文本动态读取。段位/效率/伤害的联动验证命令：`/bmfstown skillxp`。

### 4.6 需求表达系统（气泡 + 右键 UI 双层）`【已定 D14】`

> **v0.3 修订**：v0.2 的「不用 UI，玩家不打开任何界面也能玩懂」**被推翻**。
> 原因：机制复杂度已经超过气泡与自言自语能承载的上限。
> 气泡适合表达"此刻状态"，不适表达"为什么这样、我该怎么改"。

#### 4.6.1 双层表达模型的职责划分

| 层 | 载体 | 回答的问题 | 何时出现 |
|---|---|---|---|
| **外层（低精度）** | 头顶气泡、自言自语、行为暗示 | **"他现在怎么样？"** | 随时，无需操作 |
| **内层（高精度）** | 右键 UI 面板 | **"为什么会这样？我能做什么？"** | 玩家主动右键 |

> **判定口诀**：
> - 一个符号/一句话说得完 → **气泡**
> - 需要解释、需要对比、需要操作 → **UI**
>
> **气泡是"症状"，UI 是"病历"。** 玩家可以永远不看 UI，但看了就能立刻明白该做什么。

#### 4.6.2 外层：气泡与自语

| 手段 | 示例 | 用途 |
|---|---|---|
| 头顶气泡 | 🍣 饿 / 💤 困 / ❗ 有事 / ❓ 找不到活 / 💢 不满 | 状态提示，无需阅读 |
| 自言自语 | "……这屋里连根竹子都没有，睡不着。" | 表达环境偏好未满足 |
| 主动对话 | "你最近一直在照顾我啊……" | 表达满意度变化 |
| 行为暗示 | 走到食物区却空手而归，垂头 | 表达饥饿 |
| 名字标签 | 显示名字而非"村民" | 建立身份 |

**气泡规则**：
- 同一时刻**最多一个**气泡，按优先级覆盖（饿 > 不满 > 有事 > 困 > 无）
- 气泡**不携带数字**，只有图形
- 气泡不是常显，状态持续时周期性闪现（如每 5 秒一次，持续 2 秒）

#### 4.6.3 内层：镇民 UI 面板（v0.3 详细化）

**触发**：玩家空手右键镇民（手持食物仍是喂食，见 §4.3）。

> **v0.3 修订**：v0.2 时这里只是"v0 草案"的一行表格。
> 用户明确要求"镇民需要 UI，可以浏览这些信息"，现按 §4.1.2 的属性分组设计完整面板。

##### 4.6.3.3 状态区的显示规则（关键）

| 属性 | 图形 | 文本分档 |
|---|---|---|
| **血量** | ❤ 实心 / ♡ 空心（10 格） | 健康 / 带伤 / 重伤 |
| **饥饿** | ♥ 实心 / ♡ 空心（5 格，粗粒度） | 很饱 / 正常 / 有点饿 / 很饿 / 快饿晕了 |
| **心情** | 表情符号 | 心情很好 / 心情不错 / 一般 / 有点烦 / 很不高兴 |

**为什么血量和饥饿用不同精度**：血量是原版概念，玩家已经习惯 10 格心；饥饿是新概念，用 5 格粗粒度防止玩家算"还能撑几分钟"。

##### 4.6.3.4 身份卡的"标签云"规则

| 规则 | 说明 |
|---|---|
| 只显示**名称**，不显示内部 id | "🌹 花" 而非 "`minecraft:flowers`" |
| 爱好按权重排序 | 权重 3 的排前面，最多显示 5 条 |
| 厌恶必须至少 1 条 | 与 §4.1.3 第 2 条一致，**空着就是 bug** |
| 用图标 + 文字双重编码 | 只看图标也能扫出大概 |

##### 4.6.3.5 UI 的三条硬规则

1. **不显示精确数值**。饥饿显示"有点饿/很饿/快饿晕了"，不显示 `37/100`。
   → 理由见 §4.6.4，仍保留对"算最优解"的警惕，只是放宽了呈现形式。
2. **不显示熟练度进度条**。只显示称号。玩家能感知"他变强了"，但不能算出"还差多少升级"。
3. **UI 里只有"可执行的操作"和"可理解的描述"**，不放纯统计数据。

##### 4.6.3.6 技术选型 `【待定 D26】`

| 方案 | 适用 | 代价 |
|---|---|---|
| `Screen`（只读） | v0 面板不含物品槽 | 简单，一两百行 |
| `AbstractContainerScreen` + `Container` | 需要拖动物品（如让玩家把食物放进他的背包） | 复杂，需要 `MenuType` 注册、服务端同步 |

**倾向 v0 用 `Screen`**：面板里物品栏是**只读展示**，操作通过按钮（不通过拖动）。
如果将来要"把食物塞进他背包"，再升级为 `Container`。

`【存疑 Q25】` 见第 11 章：气泡与 UI 的职责边界在实现中会不断模糊。
`【存疑 Q27】` 见第 11 章：Screen 与 Container 的返工风险。

#### 4.6.4 仍然明确禁止的（v0.3 保留）

- ❌ 头顶红字提示具体原因（"住宅条件不满足：缺少竹子"）
- ❌ 精确数值条（饥饿 37/100、熟练度 62%）
- ❌ 需要打开面板才能知道"他现在饿不饿"（气泡必须能独立表达紧急状态）

> **理由**：数字一旦精确暴露，玩家就开始算最优解，情感连接会死。
> v0.3 的放宽是"允许面板存在"，不是"允许数字外露"。

`【存疑 Q24】` 见第 11 章：UI 引入后的信息过载风险。

### 4.9 城镇系统（v0.3 新增，v0.4 落地重写，L7 归属层）

> **用户定义**："需要某种东西划定一个城镇范围，为城镇选范围、命名，然后镇民被维护在一个列表，在镇民 UI 中可以给他分配他的城镇。"
> "吃饭的地方是公用的和城镇进行自动绑定，住所要给每个人单独分配。"
>
> **v0.4 注**：本章自 4.9.2 起已按实际实现重写。v0.3 的"城镇核心方块 + 球形半径"方案（原 D22/D27）被 **镇界魔杖 + 城镇手册** 方案取代。

#### 4.9.1 城镇是什么

**城镇 = 名字 + 范围（长方体） + 子区域列表。**

不是"一堆建筑的集合"，而是一个**有边界的容器**。v1 的城镇记录：

```java
record TownZone(UUID id, String name, TownWandMode kind, BlockPos min, BlockPos max)
// Town: UUID id, String name, String ownerName, String dimension,
//       BlockPos min, BlockPos max, Map<TownWandMode, List<TownZone>> zones, long createdAt
```

| 项 | 设计 |
|---|---|
| **创建方式** | 镇界魔杖（`town_wand`）两次右键取两点 → 确认，形成**两点长方体**（D22 已定，修订自球体半径） |
| **存储位置** | `TownSaveData extends SavedData`，挂在世界数据存储（存档级，不依赖区块加载）；`setDirty()` 于每次变更 |
| **排序** | 城镇列表按 `createdAt` 升序（D31）——新建的排在手册后面 |
| **重叠约束** | 新城镇范围与已有城镇重叠时拒绝创建；子区域必须完整落在所属城镇内部 |
| **单人/多人** | v1 仅单人完整可用（预览图依赖本地存档目录），联机时静默降级 |

#### 4.9.2 两件套交互流程（D27 已定，修订自城镇核心方块）

| 物品 | 交互 | 行为 |
|---|---|---|
| **镇界魔杖** `town_wand` | 潜行+右键 | 切换模式：城镇 / 食堂 / 住所 / 工作 |
| | 右键方块 | 记录选点（第一点 → 第二点） |
| | 两次选点后右键 | **确认创建**：城镇模式 → 检查重叠 → 自动命名"新城镇 N"；区域模式 → 必须在某个城镇内 → 自动命名"食堂 N"等。成功/失败均清空两点并提示 |
| **城镇手册** `town_handbook` | 右键 | 打开账本 UI（查看 / 改名 / 删除，见 4.9.3） |

**网络同步**（5 个 payload）：`WandMode`（服务端下发当前模式）、`HandbookRequest`（客户端请求全量数据）、`HandbookSync`（服务端下发文本行格式全量数据 + 是否打开 UI）、`HandbookRename`、`HandbookDelete`。数据用 `T|...` / `Z|...` 文本行格式而非 Codec —— 牺牲一点优雅换取可调试性。

#### 4.9.3 城镇手册 UI（v0.4 已实现）

自定义 256×180 宽开账本贴图（皮革封面 + 粗糙纸纹 + 左右短边红色缝合线，贴合原版书本风格）。

| 分区 | 内容 |
|---|---|
| 左页 | 城镇信息（名字/主人/维度/范围）+ 子区域列表（可选中）；**一页一城镇**，翻页查看 |
| 右页 | 顶部**领地预览图**（创建时自动截取玩家主视角，半分辨率存储）；下方显示选中区域详情 / 改名框 / 删除确认 |
| 翻页 | 左右下角**书页卷角**效果（凹陷弧形折页，参考原版书翻页），仅在有上/下一页时显示 |
| 按钮 | 全部为"墨水按钮"（自绘矩形+文字，与书同图层，避免原版 Button 控件层漂移）；右上角 ✕ 关闭 |
| 删除 | **两步确认**（D29）：第一次点"删除" → 右页显示红色警告区"『X』将被永久删除！这是真的会很久！！无法撤销！（原版删存档也是这么警告你的，这次也一样）"→ 点"永久删除"才执行；确认后按钮状态完整复位（防止连续误删） |

### 4.10 心情与好感度（v0.3 新增，L4 状态层）

> **用户定义**："心情有一个初始值，在满足他的爱好……喜欢的东西和不喜欢的做差值，大于零的情况下，每天能上涨。或者玩家达成某些任务也可以上涨。"

#### 4.10.1 为什么必须拆成两个数值（D21 已定）

| | 心情 `mood` | 好感度 `affection` |
|---|---|---|
| **对象** | 他现在的状态 | 他对**玩家**的态度 |
| **时间尺度** | 今天 / 这几天 | 长期（几十天） |
| **波动** | **会**（饿了掉、住得好涨） | **几乎不**（喂食、帮忙、送礼才涨） |
| **玩家感知** | 头顶气泡 💢 | 台词变亲昵、称呼变化 |
| **掉了会怎样** | 罢工、抱怨 | 拒绝配合、说话冷淡 |

**如果合并**：一个镇民饿了两顿就"不爱你了"，这不合理；而"他很信任你但今天心情差"这种层次就消失了。

#### 4.10.2 心情的计算

**初始值**：50（中性偏正）

**每日结算（游戏内每天，约 20 分钟）**：

```
delta = 爱好满足得分 - 厌恶满足得分

满足得分 = Σ(每个已满足的爱好 × 权重)      // 权重 1~3
厌恶得分 = Σ(每个已存在的厌恶 × 权重)

if (delta > 0)  mood += min(delta, 5)        // 每天最多涨 5
if (delta < 0)  mood -= min(-delta, 5)       // 每天最多跌 5
mood = clamp(mood, 0, 100)
```

**事件驱动（即时修正）**：

| 事件 | 变化 |
|---|---|
| 吃到喜欢的食物 | +2 ~ +5 |
| 吃到讨厌的食物 | −3 ~ −6 |
| 饿了却找不到食物 | −5 |
| 玩家帮他修了房子 | +10 |
| 住所被破坏 | −15 |

#### 4.10.3 心情的分档与表现（不给数字）

| 档位 | 区间 | 气泡 | 行为 |
|---|---|---|---|
| 心情很好 | 80~100 | ✨ | 走路带跳、主动搭话 |
| 心情不错 | 60~79 | 😊 | 正常干活，偶尔哼歌 |
| 一般 | 40~59 | （无） | 正常 |
| 有点烦 | 20~39 | 💢 | 干活变慢，叹气 |
| 很不高兴 | 0~19 | 😠 | **罢工**，蹲在原地 |

#### 4.10.4 好感度（`affection`）的成长

**初始值**：0（陌生）

| 行为 | 变化 | 上限约束 |
|---|---|---|
| 喂食（喜欢的食物） | +1 | 每天最多 +3 |
| 喂食（普通食物） | +0.5 | 同上 |
| 完成他的心愿 | +10 | — |
| 帮他处理危险（打死怪物） | +2 | — |
| 攻击他 | **−10** | — |
| 长期不喂 | −1/天 | 最低 0 |

**分档**：

| 区间 | 态度 | 表现 |
|---|---|---|
| 0~19 | 陌生 | "……" |
| 20~39 | 认得 | 会点头 |
| 40~59 | 熟悉 | 主动打招呼 |
| 60~79 | 亲近 | 称呼变亲密、分享八卦 |
| 80~100 | 信任 | 会主动献礼物、说心事 |

#### 4.10.5 两者的交互

```
心情低  + 好感度高  →  "我知道你是好意，但我今天真的不想动"（会解释，不会记恨）
心情低  + 好感度低  →  直接罢工，不解释
心情高  + 好感度高  →  超额干活、送东西
```

**这条是设计的灵魂**：它让"养久了"有实际回报——同样是饿肚子，熟人和陌生人反应不一样。

`【存疑 Q33】` 见第 11 章：心情的每日结算是按服务器时间还是世界时间。

## 7. 体验设计

### 7.0 实现顺序（v0.3 修订）

> 依据 §4.0.2 的层间依赖，**实现顺序与章节顺序不同**：

```

   ↓
S2 劳动 —— 第一个专长（L2）                        ⬅️ 下一步
   ↓

   ↓

   ↓

   ↓

   ↓
S7 表达完善：右键 UI（L6）
   ↓
S8 记忆（L5）
```

> **v0.3 相比 v0.2 的最大顺序调整：劳动先于饥饿。**
> 因为"吃饱了才肯干活"这个因果，需要先有"干活"才有意义。

### 7.1 玩家第一小时

```
1. 玩家在自己的基地旁，看到一个陌生居民出现
2. 居民头顶冒出一个气泡：🍞
3. 玩家拿出面包给它 → 居民说："谢了，我叫阿竹。"
4. 玩家右键空床 → 阿竹走过去躺下
5. 第二天，阿竹说："这附近要是有竹子就好了……"
6. 玩家去种竹子 → 阿竹说："昨晚睡得真好。"
```

**整个过程玩家不需要打开任何界面**（但可以打开，见 §4.6）。
气泡足以支撑"第一次见面"的全部交互，UI 是**深入养成时才需要**的东西。

## 11.2 存疑项（先记录，不解决）

### 内容与识别

| 编号 | 问题描述 |
|---|---|
| **Q1** | **三级识别策略的冲突与开销**：标签与组件推断结果冲突时以谁为准？每次查标签的性能开销能否接受（高频消耗场景）？缓存粒度怎么定？ |
| **Q2** | **自定义标签的维护成本**：本 mod 定义一套语义标签（甜食、肉类……），但整合包作者不一定会填。不填时靠默认推断，推断出错的概率有多大？玩家会不会觉得"它连这个都不认"？ |
| **Q6** | **变种识别的跨 mod 可靠性**：猫的 11 种变种用实体数据识别，如果某个 mod 加了新变种（如新毛色的猫），本 mod 是否该视为"未知变种"，还是归入"猫"这一大类？ |
| **Q7** | **食物品质的跨 mod 可比性**：不同 mod 的 nutrition/saturation 数值尺度不一致（有的 mod 一个面包饱食度 20，有的只有 2）。跨 mod 比较时是否公平？是否需要归一化？ |

### 行为系统

| 编号 | 问题描述 |
|---|---|
| **Q3** | **行为抽象的边界**：8 个原语是否足够？什么样的需求会逼着加第 9 个？一旦开始加，会不会滑向"自研脚本语言"？如何判定"该加"还是"该砍"？ |
| **Q4** | **行为原语的"机器人感"** ⭐：这是最重要的体验隐患。同一套原语驱动的居民，看起来会像机械地重复动作。需要"表现层"（动画、动作停顿、发呆、抬头看天）来拉开差距。**但表现层的成本有多高？v0 是否值得先做最低限度？** |
| **Q8** | **原语与寻路的耦合**：`MINE`/`PLACE`/`INTERACT` 都需要居民走到目标前。如果目标是 10 格外的方块，寻路失败怎么办？重试？放弃？换目标？这套失败处理会影响体验（居民反复卡住是最容易让玩家失去耐心的 bug） |
| **Q9** | **多原语的时序与中断**：居民正在 `WANDER`，突然饿了要 `CONSUME`，中途又被玩家右键打断。优先级怎么定？中断后原来的行为队列是否继续？ |
| **Q10** | **"看不见就不 tick"与"玩家期待"的冲突**：玩家去挖矿两小时回来，发现居民什么都没干（因为不在加载区块内）。这符合直觉但也可能让玩家觉得"他们在偷懒"。是否需要"离线产出结算"作为补偿？ |

### 熟练度

| 编号 | 问题描述 |
|---|---|
| **Q5** | **熟练度曲线**：递增多快？软上限在哪里？"大师"需要多少小时？如果太慢玩家放弃，太快则没有长期目标。需要实际试玩才能定。 |
| **Q11** | **熟练度的"质量层"具体是什么**：厨师做出更高品质的食物——但食物品质由 `DataComponents.FOOD` 定义，我们能否"修改"它？如果不能，"质量"如何体现？额外产出？额外物品？ |
| **Q12** | **熟练度的跨专长迁移**：一个"园丁"改行当"厨师"，熟练度清零还是部分保留？如果清零，玩家会觉得"养了这么久白养了"；如果保留，则专精失去意义。 |
| **Q13** | **熟练度是否会被"刷"**：玩家建一个自动化的"练级场"（比如让居民反复种同一种花），是否能绕过"拓展内容"的设计意图？递减机制能否真正阻止？ |

| **Q14** | **对话文本的量级** ⭐：每个组合都要有"初见/满意/不满"等台词。若组合数 1700+，靠组合生成台词必然重复，玩家很快会听腻。**是否需要"模板 + 变量"的台词生成？模板化后如何避免"一眼看出是模板"？** |
| **Q15** | **名字的生成与记忆**：随机名字（"阿竹""老陈"）玩家能记住吗？需要多奇特？名字是否需要与性格匹配（如"阿竹"听起来像安静的人）？ |
| **Q16** | **"记得玩家做过什么"的记忆边界**：记多少条？记多久？记满了怎么办？记忆作为"对话素材"是否会泄露玩家不知道的信息（比如"你上周喂了我 12 次"这种精确统计会显得诡异）？ |
| **Q17** | **玩家的情感阈值**：以上所有设计都假设"玩家会对 NPC 产生情感"。但部分玩家不会——他们只关心效率。**对这类玩家，mod 是否还有吸引力？是否需要一条"纯效率"的路径？** |

### 系统与平衡

| 编号 | 问题描述 |
|---|---|
| **Q18** | **消耗与产能的量级匹配**：自动农场一小时数百食物，如果居民一天只吃 10 个，永远消耗不完。**究竟要多少个居民才能吃掉一条 Create 产线？** 如果答案是"几百个"，那居民数量上限（D4）就与需求冲突。 |
| **Q19** | **NPC 与 Create 的边界在实际操作中会模糊**：理论上"装饰性建造"归 NPC、"物流"归 Create，但玩家可能想让 NPC 去传送带上取货。这种"跨界需求"是否要支持？支持则边界失效，不支持则玩家觉得"不智能"。 |
| **Q20** | **多人服务器**：多个玩家的聚落如何共存？居民归属谁？玩家之间能否"共享"居民？如果一个玩家离开服务器，他的居民怎么办？ |
| **Q21** | **与"其他殖民/村民 mod"的兼容**：玩家很可能同时装 MineColonies、MCA、Villager Names 等。居民是否会与它们冲突（比如原版村民职业被本 mod 修改）？是否需要"隔离"策略？ |

### 表现层（本次明确留后）

| 编号 | 问题描述 |
|---|---|
| **Q22** | **表现层的实现方案**：原版村民模型的动画能力有限（只有手臂摆动、走路、头部转向）。要做出"蹲下摸叶子""抬头看天""擦汗"，是否需要自定义模型与动画？如果用原版模型，能做到什么程度？ |
| **Q23** | **表现层的成本与收益比**：做一个"工作动作"动画，成本是多少？玩家能感知到吗？还是说"少动两下"和"多做两个动作"在体验上没有区别？**这需要在原型上验证，不能凭感觉。** |

### UI 与表达（v0.3 新增）

| 编号 | 问题描述 |
|---|---|
| **Q24** | **UI 引入后的信息过载** ⭐：面板里放"状态 + 身份 + 当前行为 + 工作操作 + 归属"，一屏塞得下吗？如果塞不下要分页/分标签，而分页本身又是复杂度。**玩家的真实需求是哪个字段？其余字段能否外移到气泡或干脆不要？** |
| **Q25** | **气泡与 UI 的职责边界会不断模糊**：现在规定"气泡说症状、UI 说原因"，但实现中每个新状态都会问"这个该放哪"。缺少一条机械可判的规则（如"是否需要玩家做出选择"）。没有这条规则，最终会变成两边都放，玩家看到重复信息。 |
| **Q26** | **"模糊描述"的粒度**：饥饿说"有点饿"够用吗？如果玩家想知道"还能撑多久"，模糊描述无法回答。是否需要一个"趋势"指示（如 ↓↓ / ↓ / → / ↑）？趋势比数值模糊，但比纯形容词有用。**这类中间形态是否比二元选择（全模糊/全精确）更好？** |
| **Q27** | **UI 的可写性**：NeoForge 的 `AbstractContainerScreen` 与自定义 `Screen` 是两套东西。如果面板只读（不涉及物品槽），用 `Screen` 更简单；一旦需要"从玩家背包取食物放进去"，就得做 `Container`。**v0 该选哪条？选错会返工。** |
| **Q28** | **甜咸互斥的误伤**：如果"咸 = 非甜非素"，那 `cooked_beef`（熟牛肉）会被判成咸食。但一个"爱甜食"的镇民吃牛排时，应该算"不喜欢"还是"无感"？**三态（喜欢/无感/讨厌）比二态（甜/非甜）更安全，但需要每个维度都定义"讨厌"边界。** |
| **Q29** | **`c:foods/candy` 的语义污染**：我们往 `c:` 命名空间写入自定义内容，虽然 `replace: false` 不会覆盖，但如果另一个 mod 也定义了这个标签且语义不同（比如它认为 cocoa_beans 不算甜），会互相干扰。**是否应该改用 `bmfstown:food/sweet` 私有命名空间更安全？代价是无法与他人共享。** |
| **Q30** | **农夫乐事联动的维护成本**：`required: false` 的条目会随对方 mod 版本变动而失效（物品被改名/删除）。**没有编译期检查，只能靠运行时日志。是否需要一套启动自检，把"本该存在但没找到"的条目报警？** |
| **Q31** | ~~城镇范围的"穿墙"问题~~ **v0.4 已消解**：D22 修订为两点长方体后不再有"球体穿墙"，但长方体同样可能"隔墙包含"（垂直方向重叠的不同楼层）。若未来镇民逻辑依赖"在城镇内"，需重新评估是否加连通性判定 |
| **Q32** | **"喜欢的人"的双向性**：A 喜欢 B，B 是否也知道？如果单向，玩家要怎么发现？如果双向，关系网会变成 N² 复杂度。**这是 §4.8 宠物系统之外最贵的一块，v0 明确不做，但数据结构要预留。** |
| **Q33** | **心情每日结算的时钟**：按"服务端世界时间"（`level.getDayTime()`）还是"玩家登录时长"？如果按世界时间，玩家睡觉跳过夜晚算不算一天？如果按登录时长，多人服务器里每个人的"一天"不同步。**这直接影响"离线不惩罚"（D6）能否成立。** |
| **Q34** | **UI 的物品栏是否可交换**：v0 计划只读展示。但玩家会本能地想"我要把我的种子放他背包里"。**完全不支持会不会让人觉得"这 UI 是死的"？** 折中方案：只读 + 一个"投喂种子"按钮（走交互，不走拖拽）。 |
| **Q35** | **城镇数量上限**：一个世界能有几个城镇？如果无限制，玩家会到处扔核心。如果有限制（如 5 个），玩家想建第二个镇子会被卡住。**这与 D4（居民数量上限）耦合。** |

### 12.3 技术备忘（写给将来改代码的人）

- 索敌 Goal 节流**必须用 Goal 自持计数器**，不能用 `tickCount % N`——
  原版按 `(tickCount+实体ID)%2` 单双号调度，绝对时间门对奇数 ID 实体永不触发
  （v0.5 踩过的坑，详见 WarriorGoals 注释）；
- 菜单按钮开关类状态走 `SynchedEntityData`，不走菜单 `ContainerData`（同步不可靠）；
- 客户端交互类（站岗选点、跟随开关、perk 选档）走自定义 payload，服务端校验后落账；
- 熟练度阈值 = 存档语义：只增不改（SkillTiers 注释）；
- 配置只放"玩法数值"，不放 UI 坐标/协议常量/存档格式耦合值；
- **效率曲线是纯代码常量**（`SkillTiers`），与 perk 的 `perk.*` 配置刻意分开——曲线动一刀就破坏存档间的可比性；
- 嘲讽红罩的状态同步模式（S→C 广播 UUID+截止游戏时间，客户端按本地时间轴过期，断线清空）可复用给以后所有"瞬态可视化"需求；
- NeoForge API 随版本改名频繁（如 `LivingChangeTargetEvent.getNewTarget` → `getNewAboutToBeSetTarget`），报"找不到符号"先查 PR 记录再怀疑自己代码；
- 语言文件里含 `%` 的文案必须 `%%` 转义，否则整条译文变 "Format error: 原文"。
